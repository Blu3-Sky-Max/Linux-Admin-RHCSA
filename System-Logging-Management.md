## 1. rsyslog — System Logging Daemon

System logging captures messages generated by the kernel, services, commands, applications, and system events, then forwards them to log files for security auditing, troubleshooting, and monitoring.

The daemon responsible is `rsyslogd` (Rocket-fast System for Log processing). It is multi-threaded with support for enhanced filtering, encryption-protected message relaying, and extensive configuration options.

| Component | Location |
|-----------|---------|
| Primary config | `/etc/rsyslog.conf` |
| Drop-in configs | `/etc/rsyslog.d/` |
| Default log directory | `/var/log/` |


### 1.1 Validate the rsyslog configuration

Before restarting the daemon, always validate the config syntax:

```bash 
$ sudo rsyslogd -N 1
rsyslogd: version 8.2412.0-1.el10, config validation run (level 1), master config /etc/rsyslog.conf
rsyslogd: End of config validation run. Bye.
``` 
`-N 1` runs a dry-run validation without actually starting the daemon.

## 3. Custom Message Injection with `logger`
`logger` writes entries directly into `/var/log/messages` (via rsyslog). It is useful for injecting markers during scripts or manual testing.

### 3.1 Log a message with the `process ID` and `USER`

```bash 

$ logger -i "Usman is stil sitting with terminal name $USER"
```
### 3.1.1 Verifying output 
```bash
$ sudo grep "Usman" /var/log/messages
Mar 31 16:26:37 localhost blu3sky[17187]: Usman is stil sitting with terminal name blu3sky
```
`-i` includes the PID of the logger process in the log entry. The format is: `timestamp hostname user[PID]: message`.


### 3.2 Pipe output into the system log

```bash

$ echo “This is $LOGNAME adding this marker on $(date)” | logger 
```
### 3.2.1 Verifying output 

```bash
  
$ sudo grep "Mon Mar " /var/log/messages
Mar 30 16:49:43 localhost gnome-shell[2448]: GNOME Shell started at Mon Mar 30 2026 16:49:42 GMT-0400 (Eastern Daylight Time)
Mar 30 17:14:52 localhost blu3sky[6561]: “This is blu3sky adding this marker on Mon Mar 30 05:14:52 PM EDT 2026”
```
Piping into `logger` is useful in shell scripts to mark execution points in the system log without needing special logging libraries.

## 4. Log Rotation
Log rotation prevents `/var/log/` from filling up the disk. The `logrotate` utility is triggered daily by a systemd timer.

### 4.1 Inspect the logrotate timer

```bash 
$ systemctl cat logrotate.timer 
# /usr/lib/systemd/system/logrotate.timer
[Unit]
Description=Daily rotation of log files
Documentation=man:logrotate(8) man:logrotate.conf(5)

[Timer]
OnCalendar=daily
RandomizedDelaySec=1h
Persistent=true

[Install]
WantedBy=timers.target
```
the logrotate invoke the logrotate.service and config located at /etc/logrotate.conf 

### 4.2 List all rotation configs

```bash
$ ll /etc/logrotate.d
total 60
``` 

### 4.3 Inspect firewalld rotation policy

```bash 
$ cat /etc/logrotate.d/firewalld 
/var/log/firewalld {
    weekly
    missingok
    rotate 4
    copytruncate
    minsize 1M
}
```
This rotates `/var/log/firewalld` weekly, keeps 4 archived copies (one month of history), and only rotates if the file is at least 1MB. `copytruncate` copies the log then truncates it in place — used when a service keeps the file handle open.

### 4.4 Inspect btmp rotation policy (failed login attempts)

```bash 
$ cat /etc/logrotate.d/btmp 
# no packages own btmp -- we'll rotate it here
/var/log/btmp {
    missingok
    monthly
    create 0660 root utmp
    rotate 1
}
```
Rotates monthly, keeps only 1 archive, recreates the file with permissions `0660` (owner root, group utmp, no access for others).

## 5. systemd Journal (`journald`)

`journal` a systemd-based logging service for the collection and storage of logging data.`journald` is the systemd-native logging service. It collects structured log data from all sources — kernel, services, and user processes — and stores it in a binary format under `/var/log/journal/`.

| Component | Location |
|-----------|---------|
| Journal logs | `/var/log/journal/` |
| Configuration | `/etc/systemd/journald.conf` |

Unlike rsyslog which writes plain text, the journal stores structured fields (priority, facility, PID, unit name) queryable with `journalctl`.

### 5.6 Filter by priority since today
```bash

$ sudo journalctl --since today -p warning -r | head -2 
Mar 31 16:46:36 localhost.localdomain systemd-logind[944]: Existing logind session ID 3 used by new audit session, ignoring.
Mar 31 16:46:20 localhost.localdomain systemd-logind[944]: Existing logind session ID 3 used by new audit session, ignoring.
```
`-p warning` filters to warning level and above (warning, error, crit, alert, emerg). `-r` reverses output — newest first.
 
**Priority levels (low to high):**

| Level | Number | Meaning |
|-------|--------|---------|
| `debug` | 7 | Verbose debugging |
| `info` | 6 | Informational |
| `notice` | 5 | Normal but significant |
| `warning` | 4 | Non-critical warnings |
| `err` | 3 | Errors |
| `crit` | 2 | Critical conditions |
| `alert` | 1 | Immediate action required |
| `emerg` | 0 | System is unusable |
